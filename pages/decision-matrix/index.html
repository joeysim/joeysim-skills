Make your agent show its work.

Decision Matrix is a skill for coding agents. Ask your agent to compare options, and it rates each one against the same criteria. Every rating cites its evidence. Unknowns stay unknown. You get one clear next step.

npx skills add joeysim/joeysim-skills --skill decision-matrix

Then ask your agent: Create a decision matrix.

Version 1.7.0. Works in Claude Code, Codex, and other agents that read Agent Skills. No Node.js? Download the ZIP.

Every decision, on the record.

In a project, the agent saves each decision to docs/decisions/ as Markdown. A bundled script builds a matching HTML page for each one, and an index that links them all.

  • Each page opens with the decision. The matrix comes next, and the method comes last.
  • When you choose an option, the decision is Locked and your pick shows as Selected.
  • New evidence updates the decision and adds a revision. The history stays.
  • Options, tools, and models link to their real pages.

How your agent works through a decision

  1. Frame the decisionIt states the question, the baseline, and what a good outcome is.
  2. Set shared criteriaEach criterion is a question with a source: your words, an inference, or a labeled assumption.
  3. Rate every optionOne rating per criterion, with the evidence beside it. No invented weights.
  4. Recommend a next stepOne option, the main trade-off, and what would change the answer.
  5. Log itIn a project, the decision goes to the log as Markdown and HTML.

Install

  1. Run this in your project folder:
    npx skills add joeysim/joeysim-skills --skill decision-matrix
  2. To add the skill for your user account instead, so that every project has it, add -g.
  3. Ask your agent: Create a decision matrix. Name your options, or let the agent find them.

No Node.js? Download the ZIP, and move the decision-matrix folder into ~/.claude/skills/ for Claude Code, or into ~/.agents/skills/ for Codex and other agents.

Visual output rulesExperiment rulesWorked example

Build a comparison that explains the next useful action and what evidence could change it. This standalone method requires no specific application, service, or database.

Use this method when alternatives could materially change the result, even without an explicit request. For routine choices, give a direct answer unless the user requests a matrix. Keep generated files in the local workspace. Publish only to a destination that the user names. Stay within the current task and authority. A comparison or a recommendation alone does not authorize implementation, spending, a scope change, or more resources.

Start from the available context

The user does not need to supply options, criteria, or a request format. "Create a decision matrix" is enough when the conversation identifies the decision. Infer the decision question, candidate options, and criteria from the user's goal and available evidence. State material assumptions explicitly. If the decision subject is missing or ambiguous, ask one focused question about the goal. Otherwise, ask only when a fact or preference that only the user has would materially change the next action. When an explicit assumption is enough, continue authorized, reversible work.

When the user names options, compare only those options. When the named options exclude the current approach, add it as the no-change option. Mention another credible option in one line outside the matrix when it could change the decision. When the user names no options, generate credible alternatives. Keep option generation separate from evidence collection. A generated option has no observed results until evidence supports them.

Frame the decision

  1. State the decision question and the intended outcome.
  2. Describe one representative task that all options must address.
  3. Identify the current workflow or another justified baseline.
  4. Record required capabilities, resource limits, available evidence, and material uncertainty.

Separate the delivery format from the approach to the problem. For example, a website is a format, while guided steps and direct editing are different approaches.

Establish shared criteria

Use observable outcomes that distinguish useful options. Give each criterion one measure. Split a criterion that joins two outcomes. Check that each criterion can separate the options. When every option would get the same cell, make the criterion sharper. Assign each criterion a stable identifier, a clear label, a required flag, and a source. Express ambiguous criteria as answerable questions. For example, replace "Speed" with "Can this meet the agreed deadline?" Define what better means for each criterion, including direction, relevant thresholds, and the comparison baseline. Use existing limits or evidence for thresholds. Label any proposed threshold as an assumption.

SourceRequired explanation
UserAn exact quotation and a reference to the original request or later user input.
InferenceThe reasoning that connects the criterion to the intended outcome.
AssumptionThe revisable agent choice and its basis.

Check that each quotation actually supports its criterion. A matching quotation establishes provenance, not a valid interpretation. Keep required constraints separate from preferences. Do not present an inferred preference or implementation choice as a user requirement. Check whether a criterion unfairly favors one approach before evidence exists. Preserve required user criteria unless the user authorizes their change or withdraws the underlying direction. Record reasons for changed inferences or assumptions.

Include material concerns from affected people when the available context identifies them. Consolidate overlapping criteria without losing distinct requirements. Record known priorities among optional criteria without inventing weights. Label inferred priorities as assumptions.

Check yourself whether an option that meets every criterion would justify proceeding. Investigate remaining objections for missing constraints, unclear criteria, or disputed evidence.

Define credible options

Compare different mechanisms or explanations of the problem. When only one approach is apparent, consider its opposite or a smaller trial. Do not invent a compromise or a fixed number of options. Include the current approach as the no-change option when it remains credible. Otherwise, explain its exclusion. For a change decision, consider no action, including the benefits forgone by not acting. Use the fewest options and criteria that cover the decision. Use at most five criteria. Use more only when the user asks for the added criteria by name. The user can ask in the request for the matrix, or in a reply such as "Add cost and speed." Do not join two criteria to stay within the limit. A requirement from earlier in the conversation is an input to the criteria. It does not raise this limit. Two to four options usually fit one view. Retain more options when the decision requires them.

For each option, record:

  • A stable identifier and a title.
  • A description, only when a reader cannot tell what the option is from its title. See "Present the matrix".
  • A link to its main page, such as its home page, documentation, repository, or model card.

When you test or build options, also record a hypothesis, a falsifier, and a status for each one, as in the experiment rules. Rule out an option only when evidence shows that it fails a required constraint. Do not treat an implementation assumption as evidence against an alternative. Check relevant precedents before claiming novelty. Keep novelty unknown when no comparison supports the claim.

Investigate the uncertainty

Use existing evidence when it adequately answers the decision. Otherwise, choose the smallest comparison that could change the next action. Research, sketches, a technical check, or one interaction can be sufficient. Do not build complete products merely to populate the matrix.

An experiment compares options on a shared task. A quote, a call, or a search is a next action, not an experiment. Before you plan, run, or report an experiment, read the experiment rules. Explore every listed option before presenting a final comparative recommendation. Keep the recommendation provisional when an option remains untested or a planned result remains unavailable. When execution exceeds the request, provide the provisional matrix and the experiment plan. Do not run that experiment without the necessary authorization.

Rate every option

Rate every option against every shared criterion exactly once. Use qualitative ratings unless measurements justify numbers. Below the matrix, define what each applicable rating means for each criterion. Binary constraints need no artificial middle rating.

RatingMeaning
SupportedCited evidence supports the criterion within the stated limits.
PartialCited evidence supports only part of the criterion or includes material limitations.
Not supportedCited evidence shows a failure against the criterion.
UnknownThe available evidence does not establish the outcome.
SimulatedA model simulation supplies a provisional judgment, not a human observation.

Adapt these labels when the task needs another clearly defined scale. Keep Unknown and Simulated explicit. Use local paths, source links, test records, or identifiable user input as evidence references. Give each evidence reference an ID: E1, E2, and so on. Record each observation's method, date, and relevant scope. Explain the missing evidence for Unknown cells. Do not cite an assumption as proof of an unmeasured outcome. Separate observations, interpretations, assumptions, and unknowns. Limit human evidence to the experience actually reported or observed. Browser checks and model simulations cannot establish human effort, preference, or general usability.

Do not invent weights, measurements, or confidence percentages. Use weights only when the user supplies or accepts their meaning. If the user requests numeric scoring, define its anchors, direction, units, and evidence basis. Keep ordinal judgments distinct from measured quantities. Give a total only when the user asks for one. Never hide a failed required constraint inside an average, and do not select an option by counting favorable cells. An unknown required outcome remains unresolved, even when other ratings are favorable.

Recommend the next action

Lead with the recommendation, its main reason, and the trade-off that it accepts. Use them as the report or matrix headline. Recommend exactly one option for the current decision, and say whether to test, build, or retain it. For other decision domains, use an equivalent concrete action. When evidence cannot support a final choice, recommend one provisional next action. Use the other options as alternatives or test baselines. State the material unknowns and the condition for reconsideration, including assumptions or preferences that could change it. Check that the numbers in the headline and the recommendation match the matrix. Give the baseline, units, and time period for each numerical comparison. Flag unexplained differences before you present it as established. Preserve documented disagreement about facts, priorities, or recommendations, and say what evidence or user choice could resolve it. Do not infer consensus from silence.

Present the matrix

For a personal decision that is easy to reverse, keep the answer short. Give the recommendation, the criteria with their sources and required flags, the matrix, what could change the answer, and the evidence. Leave out option hypotheses, statuses, and the experiment plan unless the user asks for them.

Use Markdown unless the user requests another format or an existing destination requires one. Put criteria in rows and options in columns in every matrix, also in narrow layouts. Number the criterion rows 1, 2, 3, and label the option columns A, B, C. Use the same labels in the explanation. They do not replace stable identifiers. Put Recommended, in bold, at the top of the recommended option's header, above its letter and title. Put Selected there instead only when the user chose that option. Use no other chip text. Give each option a title that says what it is. Add a description only when a reader cannot tell what the option is from its title. A well-known product, brand, or place needs none, such as Tesla Model 3 or Lisbon. A label for an approach, or a niche name, needs one, such as Hybrid or Phonon 31M. A description says what the option is and how it works, in eight plain words or fewer. Do not repeat the title in the description. Give only facts that the title does not give. Put it in italic text beneath the title, inside the option header. Put the facts that set options apart, such as a trim or a fuel type, in the cells. Name each criterion after its measure or its capability. Use the user's words, such as Lease per month or Works offline. Keep the label to four words or fewer. Give its terms with its source. Do not mark required criteria in the matrix. Give the required flag with each criterion's source. Leave out a criterion row that every option passes equally, unless the user asked for that criterion. Below the matrix, list each left-out criterion that could change the choice. Give its result for all options, such as Works offline: not tested. Do not say why you left it out. Give a result that nobody tested as not tested, not as a pass. Write the matrix in plain words, for a reader who did not see the analysis. Call each thing by its common name, or by the name that the user gave it. Do not use a name that you made up during the analysis. Write each rating cell in this order:

  1. The color marker, in Markdown only.
  2. The key fact, in four words or fewer, as the first sentence. It answers the criterion directly. Use a number with its unit, yes or no, or a plain phrase, such as $42,640., Yes, but slow., or IIHS Top Safety Pick.
  3. The reason or the main limit, in one short sentence with one idea and everyday words. Put calculations and other details in ## Evidence.
  4. The evidence IDs, such as E2, E3.

Do not write the rating word, such as Supported or Partial, in the cell. The color shows the rating. Do not use bold or italic text in rating cells. Give every option the same text style. For a Simulated rating, start the key fact with "Simulated:". For an Unknown rating, make the missing evidence the key fact, such as Not tested. When the matrix has scores, add the score to the key fact, such as 0.29 s, score 5. Link each tool, framework, model, service, or standard at its first mention. Link each option title in the matrix header to the option's main page. Open the option's main page before you link it. Give only links that you opened or that a cited source gives. Do not guess an address. Link local files with paths relative to the output file. Show each rating's color in one way only, as the output format sets:

OutputRating cellColor key below the matrix
Plain MarkdownStart the cell with its marker: 🟢 Supported, 🟡 Partial or Simulated, 🔴 Not supported, ⚪ Unknown.The markers and their labels.
Visual, such as HTMLFill the cell with its background color.Color swatches and their labels.

Keep criterion sources, and any option hypotheses you show, close to the table. When you show statuses, keep exploration status and build status separate from the recommendation label. State whether the comparison is provisional or complete. A complete comparison does not prove that every required outcome passed.

Before you make visual output without the bundled script, read the visual rules.

Say each fact once, in the section that the layout gives it. Leave out lines that only say that nothing applies, such as no weights or no left-out criteria. Write one instruction per sentence, in 20 words or fewer. Keep other sentences to 25 words or fewer. Use periods, commas, colons, or parentheses instead of em dashes. Preserve necessary precision, exact quotations, identifiers, and uncertainty.

Read the worked example when distinguishing evidence, simulations, unknowns, or required constraints is difficult.

Before delivery, check criterion coverage, source support, evidence limits, constraint failures, recommendation consistency, and whether new results change ratings. Check that exactly one option header has a chip. State skipped checks and material risks.

Keep a decision log

Save each decision matrix that you make in a project folder to the project's decision log. Keep a decision without a project folder, such as a personal choice, in the answer only. For a logged decision, give the decision and the next action in the reply, with links to the decision file and its page. Do not repeat the matrix. Use the project's existing decisions folder, if it has one. Otherwise, use docs/decisions/.

Save each decision in its own file, named NNN-short-title.md. Number the files in order: 001, 002, and so on. Use this layout for each decision file, in this order:

  1. The number and title as a heading, such as # 001. Speech-out voice.
  2. The date and status, such as Date: 2026-11-10 · Status: Provisional.
  3. The decision question, in one sentence. The log index shows this sentence as the description.
  4. ## Recommendation, or ## Decision when the status is Locked: four paragraphs of one sentence each: the recommended or selected option and the main reason, then Trade-off:, Next:, and Reconsider:.
  5. ## Matrix: the matrix, the color key, and the left-out criteria that could change the choice. Then explain the rating scale and any weights in a ### Rating scale subsection.
  6. ## Criteria: the intended outcome, the shared task, and each criterion with its source and its required flag.
  7. ## Options: the baseline and the options that you ruled out. When you test the options, add the hypothesis, falsifier, and status of each.
  8. ## Evidence: the evidence limits, then the checks that you ran and did not run, one line each. When the next action is an experiment, put its plan in a ### Next experiment subsection.
  9. ## References: one list item for each page that the decision cites or links to. Give its ID, a link with the page's own title as the text, and the publisher, such as E1. [Lease offers](https://example.com/offers), Example Motors. Give the read date once above the list, or in each item when the dates differ. Do not write a bare address.
  10. ## Revisions, when the decision has revisions.

When you change a decision file that has another layout, change it to this layout. Also change its cells and references to the rules in this skill.

Use Provisional, Complete, or Locked as the status. Set the status to Locked only when the user chooses an option. Then remove Recommended, and put Selected at the top of the selected option's header. Rename ## Recommendation to ## Decision. Add a revision entry with the date, the user's words, and your earlier recommendation. Change a Locked decision only when the user reopens it.

When new evidence changes a decision, update its file. Do not make a new file. Add a ## Revisions section at the end of the file, with the newest revision first. For each revision, give the date and the new evidence or the user's words. Then give what changed, in three short bullets or fewer. Preserve earlier decisions and contradictory evidence. Do not remove compared options merely because they performed poorly.

After each change to the log, run the bundled script. Give the full path of the script and of the decisions folder:

python3 <skill folder>/scripts/render_html.py <project>/docs/decisions

It writes an HTML page beside each decision file, and an index as README.md and index.html. Make all HTML versions of a decision matrix with this script. Do not edit the files that it writes. When the user asks for HTML of a matrix outside the log, add the matrix to the log first. If the script stops because of a chip, correct the Markdown and run the script again. For any other stop, give its message to the user and ask how to continue.

Visual output

These rules apply to visual output, such as HTML. They add to the rules in "Present the matrix" in SKILL.md. The bundled scripts/render_html.py already follows them for the decision log.

Columns and chips

Give option columns equal widths across all visual tables. Use a compact, rounded chip for Recommended or Selected. Put the chip in a row above the option titles, centered over its column. Start all option titles at the same height. Use a neutral or blue chip style that differs from the rating colors. For Selected, invert the Recommended chip: use its text color as the fill, and its fill color as the text.

Option headers

Show option titles in the text color, with a dotted underline for each link, as for the evidence IDs. Show each description beneath its title, in smaller, regular-weight gray text. Keep descriptions aligned with their option columns.

Layout and color

Show previews only when they represent the compared variants. Keep text readable at narrow widths. Show the key fact of each cell on its own line, in regular weight. Show the basis and the evidence IDs below it, in smaller, fainter text. Link each evidence ID to its reference. Open links to pages outside the decision log in a new tab. Show the ## Evidence and ## References sections in smaller gray text. Use black text on light surfaces and responsive font sizes. Use clear traffic-light colors. Use green for Supported, yellow for Partial, and red for Not supported. Keep color fills distinct from the page background. Show a color key below the matrix. Keep Unknown gray or uncolored. Use yellow for Simulated with an explicit provisional label. Do not represent missing evidence as an observed middle outcome. Put a border around the recommended column and its chip. Colors and layout do not establish evidence quality.

Experiments

These rules apply when you test or build options to compare them. An experiment compares options on a shared task.

Options in an experiment

For each option, also record:

  • A hypothesis that explains why the approach could address the problem.
  • A falsifier: an observation that would weaken that hypothesis.
  • Its build status (built, unbuilt, or unknown), only when the option is something to build.
  • A local artifact or preview link for each built variant, when available.
  • Its exploration status and supporting evidence.

Use exploration status Observed, Researched, Simulated, Ruled out, or Untested. Use Researched when cited sources describe the option, but nobody observed it on the shared task. Use Ruled out only when evidence establishes a constraint violation or weakens the hypothesis enough to reject it. An unbuilt option can still have useful research or simulation evidence.

Before an experiment

Save its plan. If you cannot write files, put the plan in the answer. Give each part of the plan one line:

  • The question and method.
  • The baseline and included options.
  • The shared task, inputs, and measures.
  • Measures that require actual human observations.
  • The decision rule, including an inconclusive outcome.
  • The resource limit and stopping condition.

Use the same task and measures for comparable tests. Preserve inspectable variants when implementation affects the result.

After an experiment

Report every planned measure, including unknown results. Apply the saved decision rule to the observed evidence. Classify the result as supports, challenges, or inconclusive. Update the affected ratings before presenting the revised recommendation. Link each revision to its predecessor, new evidence, and reason for change.

Worked example

This example is fictional. Its evidence labels represent supplied records, not sources to cite in real decisions. Real matrices must link to actual evidence. This example shows the reasoning, not the layout of a decision file.

Supplied request and evidence

User request U1: "The tool must run offline and cost no more than $5 per month. I want fewer corrections."

The user supplied no options. The agent proposed alternatives from the goal and current workflow before collecting the evidence below.

  • E1: A browser test completed the editing task offline in the current form. Its recorded monthly cost is $0.
  • E2: A browser test completed the same task offline in a guided prototype. Its recorded monthly cost is $2.
  • E3: A model simulation predicted fewer corrections with the guided prototype. No person tested that prediction.
  • E4: The hosted assistant requires a network connection and costs $8 per month under the supplied terms.

Recommend testing B: delay adoption to check the predicted benefit

Test the guided prototype (B) against the current form (A) with people before adopting it. B meets the recorded technical and cost constraints and has a predicted benefit worth testing. E2–E3. Use A as the comparison baseline. The hosted assistant fails both required constraints. The guided prototype has functional evidence, but its predicted human benefit remains provisional.

Decision question: Which approach merits the next test? Shared task: Correct one erroneous value in the same sample record. Baseline: The current form. Trade-off: B may reduce corrections but costs $2 more per month than A. E1–E3. Comparison status: Provisional for human outcomes.

Rating definitions:

  • Offline: Supported requires completion without a network connection. A required network connection means Not supported.
  • Cost: Supported means at most $5 per month. A cost above $5 means Not supported.
  • Corrections: Supported requires fewer human correction attempts without reducing successful completion. This comparison rule is an assumption.
  • Equal or greater correction attempts mean Not supported for improvement. Conflicting human results can justify Partial with an explanation.
  • Missing human observations mean Unknown. A model prediction remains Simulated.

Priority: The required constraints apply before the preference for fewer corrections. The user supplied no preference between cheaper options that satisfy the monthly limit. The agent must not invent that preference or agreement among stakeholders.

Sufficiency check: Meeting the constraints and reducing corrections supports proceeding only if people can still complete the task. The comparison rule includes successful completion. Human evidence for that outcome remains missing.

Assumption: The sample editing task represents the work that needs improvement. This assumption remains revisable. It does not create a new user requirement.

Next experiment

Question: Does the guided prototype reduce correction errors on the representative task? Method: Compare both local variants with people using the same task and equivalent records. Baseline: The current form. Measures: Additional correction attempts, successful completion, and failures against required constraints. Human measures: Correction attempts and successful completion by people. Decision rule: Prefer the guided prototype if it reduces corrections without reducing successful completion or violating either required constraint. Otherwise, retain the current form or classify conflicting results as inconclusive. Stopping condition: Stop at the agreed session limit or when a required constraint fails. Resource boundary: Participant access and the session limit remain unspecified. This example authorizes no recruitment or spending.

Reconsideration condition: Relevant human observations contradict the prediction or either option fails a required constraint. A later decision must retain this record and explain any changed recommendation.

Skipped checks: No human sessions or production cost checks occurred in this fictional example. Risk: Simulated improvement may not transfer to actual use.
